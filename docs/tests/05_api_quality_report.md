# 05 — Отчёт качества MCP API Synopsis

**Дата:** 2026-08-14  
**Версия KB:** 21 документ, 271 чанк, 109 сущностей, 124 факта, 4 домена (hr, engineering, product, it)  
**Граф:** 3 узла, 6 рёбер

---

## Executive Summary

MCP API Synopsis предоставляет 12 инструментов для работы с knowledge base через Model Context Protocol. Все инструменты функционально работают и возвращают данные за приемлемое время (search: 11–143 ms). Основные проблемы сосредоточены в трёх областях:

1. **Дрейф документации** — фактические имена полей, структура ответов и поведение отличаются от `docs/api.md` во всех 12 инструментах.
2. **Качество извлечения сущностей** — email-адреса как имена сотрудников, даты как политики, Go-переменные (`tt.input`, `tt.wantErr`) как серверы.
3. **Баг cross_domain_links** в `get_entity_dossier` — одно-доменные рёбра, дубликаты, несоответствие target_entity_id ↔ target_name.

API функционально пригоден для read-only RAG-сценариев, но требует синхронизации документации и исправления багов перед продакшн-использованием.

---

## Методология

Тестирование выполнено 2026-08-14 через подключённый MCP-сервер Synopsis. Все вызовы выполнены на реальных данных KB (`data/ontology` ingested). Использованы:

- **Базовые тесты:** по одному успешному вызову на каждый из 12 инструментов + вариации параметров (доменный фильтр, пагинация, фильтры).
- **Error-кейсы:** пустой query, невалидный cursor, несуществующие ID, невалидные типы аргументов, конфликт entity_id+entity_name.
- **E2E-сценарии:** 6 сквозных сценариев (search-and-answer, entity dossier, document audit, cross-domain tracking, KB overview, analytics).
- **Кросс-доменные тесты:** проверка Hiring Policy (84/86/88), provenance, include_cross_domain.
- **Drift-анализ:** сравнение фактического поведения API с `docs/api.md`.

## Положительные находки (10)

### +1. Все 12 инструментов работают стабильно
Каждый инструмент возвращает корректный ответ при валидных входных данных. Нет крашей, таймаутов или непредсказуемого поведения.

### +2. Быстрые ответы
Search выполняется за 11–143 ms (типично 116–131 ms). Для RAG-сценариев это приемлемо.

### +3. Единообразные, понятные сообщения об ошибках
Валидация аргументов возвращает чёткие сообщения: `"Error: 'query' argument is required and must not be empty"`, `"Entity ID 99999 not found"`. Формат ошибок консистентен.

### +4. Дисамбигуация по имени
При неоднозначном entity_name возвращается список кандидатов с ID, типом и доменом:
```
Multiple entities match "Hiring Policy". Please specify one (optionally with a domain):
- Hiring Policy (id=84, type=policy) [product]
- Hiring Policy (id=86, type=policy) [hr]
- Hiring Policy (id=88, type=policy) [it]
```

### +5. Кросс-доменные ссылки с provenance
Дизайн cross-domain links продуман: method (`rule`/`equals`/`llm`), confidence, evidence — полная трассируемость происхождения связей. `get_entity_links` работает корректно.

### +6. Курсорная пагинация
Курсорная пагинация (next_cursor, total_count) работает стабильно во всех catalog-инструментах. Переход между страницами предсказуем.

### +7. Доменный фильтр и изоляция
Фильтр `domain` в search работает корректно. Изоляция доменов по умолчанию в BFS (`get_entity_relations`) предотвращает утечку данных между доменами.

### +8. Селективные флаги include_*
Флаги `include_chunks`, `include_entities`, `include_facts`, `include_cross_domain` работают (хотя entities/facts в get_document_context имеют ограничения — см. отрицательные находки).

### +9. Богатые метаданные сущностей
Метаданные извлечения содержат provider (`llm`/`regex`), rule_id, source_file, section_title — полная трассируемость происхождения каждой сущности.

### +10. Оффсеты и sequence_num в search-результатах
Наличие `start_offset`, `end_offset`, `sequence_num`, `document_path` в результатах поиска хорошо подходит для RAG-потоков (контекст, цитирование, навигация).

## Отрицательные находки (12)

### −1. Дрейф документации (docs/api.md vs реальность)
**Критичность:** Высокая  
Фактические имена полей и структура ответов отличаются от документации во всех 12 инструментах. См. drift-таблицу ниже.

### −2. Баг cross_domain_links в get_entity_dossier
**Критичность:** Высокая  
Поле `cross_domain_links` включает одно-доменные факт-рёбра (belongs_to, works_in, manages, has_role, owns_policy) с target_domain=hr. Присутствуют дубликаты и несоответствие target_entity_id ↔ target_name.

### −3. Качество извлечения сущностей
**Критичность:** Средняя  
- Email-адреса как имена сотрудников (provider="regex", rule_id="hr_email").
- Даты ("March 15 2021") как политики (provider="regex", rule_id="hr_date").
- Go-переменные (`tt.input`, `tt.wantErr`) извлечены как серверы.
- Зарплатные диапазоны ("$65,000 - $85,000") как отдельные salary-сущности.

### −4. LLM-описания непригодны для UI
**Критичность:** Средняя  
Поле `description` содержит многостраничные рассуждения LLM (~2000 слов). Не подходит для отображения в интерфейсе или API-ответах. Галлюцинации в metadata: version="1.0 (implied by context, not explicitly stated)".

### −5. Скопированные метаданные
**Критичность:** Низкая  
Сущность "Employee Benefits" (id=87) имеет metadata от Hiring_Policy.json (source_file="by-type/policy/Hiring_Policy.json", title="Hiring Policy") — скопированные, а не собственные метаданные.

### −6. get_fact_by_id: нулевое время и обрезанные цитаты
**Критичность:** Средняя  
`extracted_at` = "0001-01-01T00:00:00Z" (нулевое время Go). Цитата в sources обрезана на середине строки: `"...| Mid | $85,000 - $110,00"` — обрывается без завершения.

### −7. Валидация top_k отсутствует
**Критичность:** Средняя  
`top_k=0` и `top_k=101` не отклоняются (документация указывает constraint 1–100). Молчаливый clamp/дефолт без предупреждения.

### −8. Граф разрежен
**Критичность:** Низкая  
3 узла и 6 рёбер при 109 сущностях. `traversal_time_ms` всегда равен 0 (возможно, время не измеряется). Ограничивает полезность графовых запросов.

### −9. Релевантность поиска
**Критичность:** Средняя  
Поиск "salary" в домене hr возвращает "## Review Cycle" выше таблицы зарплат. Все score ~0.019 — почти неразличимы, что затрудняет ранжирование.

### −10. get_document_context: entities/facts не возвращаются
**Критичность:** Средняя  
Даже при `include_entities=true` и `include_facts=true` поля entities и facts отсутствуют в ответе (или возвращаются только при определённых условиях — не документировано).

### −11. Поиск по неизвестному домену — пустой результат без предупреждения
**Критичность:** Низкая  
`search(query="hiring", domain="nonexistent-domain")` → `{"results":[],"total_count":0}`. Нет указания на то, что домен не существует.

### −12. search_facts status=pending → 0 фактов
**Критичность:** Низкая  
В KB нет pending-фактов (все approved). Это ограничение данных, а не API, но затрудняет тестирование фильтрации по статусу.

## Недостающие возможности (10)

| # | Возможность | Описание |
|---|------------|----------|
| 1 | Write-инструменты | API read-only. Нет инструментов для одобрения фактов (`approve_fact`), управления сущностями, обновления KB через MCP. |
| 2 | Health/metrics через MCP | Метрики сервера доступны только по HTTP `/health`, но не через MCP-инструмент. |
| 3 | Поиск похожих чанков | Нет инструмента `similar_chunks(chunk_id)` для поиска семантически близких фрагментов. |
| 4 | Batch-запросы | Нет возможности выполнить несколько запросов в одном вызове (batch search, batch get). |
| 5 | Расширенные фильтры search | Отсутствуют фильтры по source_type, дате создания/обновления, entity-фильтр в search. |
| 6 | Объяснение скоринга | RRF-очки непрозрачны; нет информации о том, как lexical и semantic компоненты влияют на итоговый score. |
| 7 | Пагинация search-результатов | Search возвращает только top_k результатов без курсорной пагинации (ограничение 100). |
| 8 | Инструмент списка доменов/типов | Нет отдельного инструмента для получения списка доступных доменов и типов сущностей (только через catalog_overview). |
| 9 | Версия сервера/API | Нет метаданных версии в ответах; невозможно определить совместимость клиента. |
| 10 | Потоковые ответы (streaming) | MCP поддерживает streaming, но Synopsis возвращает полные ответы без потоковой передачи. |

## Рекомендации

### Краткосрочные (1–2 спринта)

1. **Синхронизировать docs/api.md** с фактическим поведением всех 12 инструментов. Это критично для разработчиков, использующих API.
2. **Исправить баг cross_domain_links** в `get_entity_dossier`: фильтровать одно-доменные рёбра, устранить дубликаты и несоответствие ID↔имя.
3. **Добавить валидацию top_k** с явной ошибкой при выходе за пределы [1, 100].

### Среднесрочные (2–4 спринта)

4. **Улучшить релевантность поиска:** калибровка score, приоритизация точных совпадений.
5. **Обрезать LLM-описания** до разумной длины; добавить raw_description для полных рассуждений.
6. **Исправить extracted_at** и обрезку цитат в get_fact_by_id.

### Долгосрочные (4+ спринта)

7. **Добавить write-инструменты:** approve_fact, manage_entities для управления KB через MCP.
8. **Реализовать health/metrics через MCP** для мониторинга без HTTP.
9. **Улучшить извлечение сущностей:** пересмотр regex-правил, исключение Go-кода из индексации.
10. **Добавить batch-запросы и расширенные фильтры search.**
